# Experiment Code and Operations Guide

Use this reference when implementing, running, debugging, or hardening research code.

## Implementation principles

1. **Make the experiment executable.** A configuration should be sufficient to reproduce a named run.
2. **Separate method, training, and evaluation.** Avoid evaluation logic that exists only inside a training loop.
3. **Preserve provenance.** Store git commit, config, environment, seed, checkpoint path, and evaluator arguments.
4. **Fail early.** Validate labels, class count, image paths, GPU binding, output directories, and checkpoint state before training.
5. **Keep raw results immutable.** Aggregation and plotting read files; they do not edit them.
6. **Prefer deterministic wrappers.** A queue script should decide whether to start, resume, wait, or stop.
7. **Avoid hidden environment effects.** `CUDA_VISIBLE_DEVICES` is not a substitute when a wrapper explicitly selects `--device`.

## Minimum run manifest

For each run record:

```yaml
run_name:
  method: method identifier
  dataset: path or canonical dataset name
  split: train/val
  model: architecture or checkpoint
  pretrained: true/false
  input_size: integer
  batch: integer
  epochs: integer
  seed: integer
  gpu: integer
  evaluator: script and protocol
  best_metric: float
  final_metric: float
  checkpoint: path
  config_hash: sha256
  code_commit: git commit
  status: running/complete/failed
```

## Queue and reboot safety

A robust queue should:

1. acquire a single-instance lock;
2. enumerate jobs and GPUs;
3. check completed epoch count from `results.csv`;
4. check whether the process is alive;
5. resume from `last.pt` if available;
6. launch only missing runs;
7. append every launch/resume event to a log;
8. never exceed the agreed GPU quota;
9. exit cleanly when all jobs complete;
10. be restorable through a reboot hook.

Stall diagnosis:

| Symptom | Check |
|---|---|
| GPU idle but process alive | dataloader, validation, NFS, CPU bottleneck |
| GPU idle and process dead | checkpoint resume, OOM, signal, queue launch loop |
| results file stale | epoch duration, process age, validation stage |
| repeated epoch number | resume failure or wrong run name |
| memory nearly full | batch, fragmentation, second process on GPU |
| loss NaN | LR, AMP, labels, class index, augmentation |

## Environment and dataset checks

Before training:

- package versions match the fact table;
- dataset image/label counts match expectation;
- class IDs are within `[0, nc-1]`;
- no duplicate labels unless expected;
- boxes are clipped and normalized;
- empty-label policy is known;
- train and val paths are not swapped;
- cache files are invalidated after label edits.

Smoke test:

1. train one small subset for one epoch;
2. restore a checkpoint and confirm epoch index;
3. evaluate a known checkpoint;
4. compare metric with an existing record;
5. generate one table/figure.

## Evaluation discipline

- Evaluate the same checkpoint selection rule across arms.
- Keep maxDets, IoU thresholds, confidence, NMS/WBF, and input size explicit.
- Report best and final metrics separately.
- Save per-class and area-based metrics.
- Do not mix native evaluator values with COCO md100 values.
- Keep prediction JSONs when storage permits; otherwise store checksums and summaries.
- Measure latency with warmup, fixed precision, batch size, and enough images.

## Statistical analysis

For key comparisons:

1. use the same seeds for paired comparisons when possible;
2. report n, mean, standard deviation, minimum, and maximum;
3. compute paired differences when seeds align;
4. use a test appropriate for n and dependence;
5. report effect size and interval;
6. state whether the test is exploratory or confirmatory;
7. do not describe small descriptive differences as significant.

## Figure and table generation

Figures should be generated by scripts that:

- read JSON/CSV result files;
- assert expected columns;
- use one protocol per subtraction;
- write both PDF and preview PNG when needed;
- avoid internal run names in labels;
- use consistent fonts, colors, and terminology;
- fail if a result is missing rather than substituting zero.

Tables should be generated or checked from result summaries. Manual edits are allowed only for formatting, not numbers.

## Code review checklist

- [ ] equations match implementation;
- [ ] default arguments match paper;
- [ ] class IDs and names match dataset YAML;
- [ ] seeds are explicit;
- [ ] device selection is explicit;
- [ ] resume preserves optimizer and epoch state;
- [ ] evaluator is independent and deterministic;
- [ ] output directories are unique;
- [ ] no private path, credential, or checkpoint is hardcoded;
- [ ] logs are sufficient to diagnose a failure;
- [ ] tests cover profile, farm construction, train smoke, resume, and eval smoke.

## Release engineering

Before releasing:

- remove private IPs, usernames, passwords, and internal project paths;
- rename internal run IDs to scientific names;
- provide a minimal public config;
- verify scripts run from a clean clone;
- document expected dataset layout;
- include environment file and package versions;
- include checksums for released result summaries;
- separate large checkpoints from the paper-result summary;
- tag the exact paper release.
